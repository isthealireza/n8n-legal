# harness

Runs the extracted n8n Code-node units against the mined QA scenarios, offline,
deterministically, with no n8n and no network.

```
node harness/run.js                      # everything
node harness/run.js --workflow wf4       # one workflow
node harness/run.js --filter delivery-key# id substring
node harness/run.js --verbose            # every check, and every skip with its reason
```

Exit code is `0` only when nothing failed.

## What is here

| file | what it is |
|---|---|
| `run.js` | the runner: selects scenarios, builds contexts, runs units, compares, reports, regenerates `invariants.md` |
| `n8n-shim.js` | a deterministic stand-in for the n8n Code-node runtime (`$input`, `$('Node')`, `$now`, `$json`, `this.helpers`) |
| `adapters.js` | one projection per scenario family — the bridge between a unit's output vocabulary and the QA workflow's `expect` vocabulary |
| `oracles.js` | **independent** re-implementations of the hash functions, so an expected digest is never copied from the code under test |
| `units/` | 59 auto-extracted units, one per Code node, byte-identical inside the `BEGIN/END VERBATIM` markers. **Do not edit.** |
| `units/index.json` | node name → file, with the sha256 of the original `jsCode` |
| `invariants.md` | generated: the live-register properties that cannot run offline, each with the query that would check it |
| `FINDINGS.md` | hand-written: production behaviour that genuinely disagrees with a scenario |
| `../.tooling/normalise-scenarios.js` | one-shot, idempotent: stamps `target` and the canonical `input` block onto every scenario |

## The three scenario kinds (four, in practice)

| kind | count | runs? |
|---|---|---|
| `pure` | 104 | yes, if it has a resolved `target` — a function of its input, no I/O |
| `integration` | 19 | no — needs live Sheets, live HTTP, or n8n's own sub-workflow dispatch |
| `invariant` | 9 | no — a property of the **live register**, not of any unit; emitted to `invariants.md` |
| `schema` | 5 | no — a fixed column layout. The runner skips it; the expected header lists are held against `fixtures/sheet-schema.json` **by review, not by code**. Nothing asserts them automatically yet. |

`schema` was not in the original three-kind design; three of the mining agents used it and
it is kept rather than forced into `invariant`, because a tab's column order is a fact
about the spreadsheet's structure rather than about its contents.

## What "skipped" means

A skip is never a pass. The summary groups them:

- **unresolved target** — no unit in `units/index.json` implements what the scenario names.
  Every one carries a `target_unresolved_reason` saying why. The commonest cases are
  QA-harness-only nodes (a marker gate, a preflight, a write gate), n8n Set-node
  expressions rather than Code nodes, administrative Sheets migrations, and one predicate
  the QA suite asserts that does not exist in production at all (see `FINDINGS.md` §2).
- **kind != pure** — `integration`, `invariant` and `schema`, per the table above.
- **needs_hash_regen** — reserved for a scenario whose expectation is a digest that cannot
  be regenerated offline. Currently empty: all five `needs_hash_regen` scenarios *are* run,
  because `oracles.js` recomputes their expected hash independently.
- **no adapter** — a scenario that was bound to a unit but whose family has no projection
  yet. Currently empty. It exists so that adding a binding without adding an adapter is
  loud rather than invisible.

## The context convention

Every runnable scenario's `input` carries a canonical block, alongside the original
QA-shaped keys (which are left in place so the derivation stays checkable):

```jsonc
"input": {
  "now": "2026-08-23T06:00:00.000Z",   // required; the shim refuses to run without it
  "items":       [ /* $input.all() — raw payloads or { json } shapes */ ],
  "nodeOutputs": { "Load Matters (Digest)": [ /* … */ ] },   // backs $('Node Name')
  // …the scenario's original register / event / ctx keys, untouched…
}
```

- `items` → `$input.all()`, `$input.first()`, `$json`.
- `nodeOutputs` → `$('Node Name').all() / .first() / .last()`. Asking for a node that is
  not registered throws with the list of names that are, rather than returning `undefined`.
- `now` → `$now` (a frozen, UTC-only, Luxon-shaped `DateTime`).
- `helpers` → optional stubs for `this.helpers.*`; unstubbed helpers throw by name.

The canonical block is generated by `.tooling/normalise-scenarios.js` from the scenario's
own QA-shaped input. Re-run it after editing a scenario's register:

```
node .tooling/normalise-scenarios.js
```

### Determinism: two clocks, both pinned

`$now` is not enough. Several units read the JavaScript global clock directly —
`new Date()` in `Build Daily Digest` (today's date, the quiet-matter and overdue
arithmetic) and in `Distil Sources` (`retrieved_at`), and `Date.now()` in `Finalise Plan`
(the base36 plan stamp). The runner therefore replaces the global `Date` with a frozen
subclass pinned to `2026-08-23T06:00:00.000Z` — the anchor the digest suite's fixtures were
frozen against — for the whole process. A unit can no more reach the wall clock than it can
reach the network. Production code is never edited to achieve this.

## How to add a scenario

1. Write `fixtures/scenarios/<id>.json` with at least:
   `id, workflow, unit, kind, source_qa_workflow, description, why_it_exists, input,
   expect, assertions`.
   Keep `input` in whatever shape the source QA workflow used; the normaliser derives the
   canonical block from it.
2. Teach `.tooling/normalise-scenarios.js` how to reach your unit: add a branch to
   `classify()` returning `{ target, adapter, items, nodeOutputs }`, or an entry in its
   unresolved table with an honest reason.
3. If the family is new, add an adapter to `adapters.js`. An adapter returns
   `{ checks, informational, consumed?, detail? }`. **Every top-level key of `expect` must
   be consumed** — as a check, or by naming it in `informational` (prose, provenance,
   notes). The runner fails any scenario with an unconsumed key. That is the rule that
   stops an assertion from being quietly dropped.
4. `node .tooling/normalise-scenarios.js && node harness/run.js --filter <id> --verbose`.

### Oracles, and why `expect` never says "whatever the code produces"

Where a scenario's expectation is a hash, `expect` carries the sentinel `"REGENERATE"` (or
a `"RUNTIME:…"` placeholder) rather than a literal, and the runner resolves it through
`oracles.js` — a second implementation written from the algorithm's description. It uses
the FNV-1a *multiply* form (`Math.imul(h, 0x01000193)`) where the units use the *shift-add*
form; the two are the same function by definition of the FNV prime, so agreement is a real
cross-check of the surrounding derivation — the basis string, its field order, the salting,
the pad width — and not a restatement of the loop under test.

The reason this matters is recorded in `fixtures/scenarios/_groupA-notes.md`: the original
delivery-key oracles were computed in Python over a real recipient address that has since
been replaced by a synthetic one, so copying the JavaScript's output would have turned five
assertions into tautologies.

## Rules this harness is built to keep

- **Never edit `units/`.** The text between the `VERBATIM` markers is the deployed node.
  A unit that misbehaves is a finding, not a bug to patch here.
- **Never weaken an assertion to get green.** If production disagrees with a scenario and
  neither the binding nor the transcription is at fault, it goes in `FINDINGS.md` and the
  scenario stays red.
- **Never resolve an expectation by asking the code.** See oracles, above.
- **An unresolved target is better than a wrong one.** A wrong binding reports a green
  result about a unit that was never exercised.
