# Live-register invariants

_Generated by `node harness/run.js`. Do not edit by hand._

These 9 scenarios are properties of the **live Google Sheets register**, not of
any unit. They have no `input`: there is nothing to feed a function, because the subject
is the register itself as it stands right now. `harness/run.js` counts them as skipped and
lists them here with the query that would check each one.

Every query below is read-only (`values:batchGet` or `values.get`). None of them writes.

## `wf4-delivery-key-is-16-char-format`

- **Workflow**: wf4  |  **Unit under protection**: Approval Gate delivery-key derivation (send_key / dry_key / communication_id)
- **Source QA workflow**: QA - Communications Delivery Key Census (`vrP4KZLwrsAbekc1`)

**Property.** Every SND- delivery key on the Communications tab is in the widened 16-hex-character format; any surviving 8-character key is a pre-F-02 legacy row that the current code can no longer match.

**Why it exists.** F-02 widened the delivery key from 32 to 64 bits. The change is deliberately not backward compatible: a Communications row written under the old 8-character key will not be matched by the new 16-character key, so the first write per approval after the change appends a second row instead of updating the first. The census counts rows by key format to size that one-time effect and to find any approval still stranded on a legacy key.

**Query that would check it.**

```
GET https://sheets.googleapis.com/v4/spreadsheets/{SPREADSHEET_ID}/values:batchGet
    ?ranges=Communications!A1%3AZ2000
    &valueRenderOption=UNFORMATTED_VALUE

then, over the returned rows:
  - Every Communications.idempotency_key beginning with SND- matches ^SND-[0-9a-f]{16}(\|DRY)?$.
  - No SND- key is in the old format ^SND-[0-9a-f]{8}(\|DRY)?$, and none is in a third shape.
  - The dry-run key is exactly the send key with the literal suffix |DRY; the two must never be confused as separate deliveries.
  - communication_id for a real send is 'COM-' + the same hash; for a dry run it is 'COM-DRY-' + the same hash.
  - The key is a pure function of approval_id, action_id, draft_id, upper-cased channel and normalised recipient - no clock, no delivery_mode, no randomness.
  - Re-deriving the key from a row's own approval_id/action_id/draft_id/channel/recipient must reproduce that row's key; if it does not, the row is hand-edited or the key has collided.
```

**Assertions.**

- Every Communications.idempotency_key beginning with SND- matches ^SND-[0-9a-f]{16}(\|DRY)?$.
- No SND- key is in the old format ^SND-[0-9a-f]{8}(\|DRY)?$, and none is in a third shape.
- The dry-run key is exactly the send key with the literal suffix |DRY; the two must never be confused as separate deliveries.
- communication_id for a real send is 'COM-' + the same hash; for a dry run it is 'COM-DRY-' + the same hash.
- The key is a pure function of approval_id, action_id, draft_id, upper-cased channel and normalised recipient - no clock, no delivery_mode, no randomness.
- Re-deriving the key from a row's own approval_id/action_id/draft_id/channel/recipient must reproduce that row's key; if it does not, the row is hand-edited or the key has collided.

## `wf4-no-unresolved-outbound-pending-or-uncertain`

- **Workflow**: wf4  |  **Unit under protection**: Approval Gate checks 7b and 7b-2 (fail-closed send blocking)
- **Source QA workflow**: QA - Communications Delivery Key Census (`vrP4KZLwrsAbekc1`)

**Property.** No Communications row is left indefinitely in OUTBOUND_PENDING or OUTBOUND_UNCERTAIN, because each one permanently blocks any further send on that delivery key.

**Why it exists.** OUTBOUND_PENDING means a run reached the send step and nothing confirmed the outcome. OUTBOUND_UNCERTAIN was added by F-04, after it was found that Mark Send Failed stamped every send-path error as OUTBOUND_FAILED - including a network timeout that may have occurred AFTER Gmail accepted the message. Because check 7c deliberately ignores OUTBOUND_FAILED so a known failure does not block a retry, an uncertain outcome was being converted into permission to send the same legal communication twice. Both states now block exactly like a duplicate, so each one is a live, human-owned obstruction that has to be counted and cleared.

**Query that would check it.**

```
GET https://sheets.googleapis.com/v4/spreadsheets/{SPREADSHEET_ID}/values:batchGet
    ?ranges=Communications!A1%3AZ2000
    &valueRenderOption=UNFORMATTED_VALUE

then, over the returned rows:
  - Zero Communications rows have direction OUTBOUND_PENDING.
  - Zero Communications rows have direction OUTBOUND_UNCERTAIN.
  - Any such row that does exist must be reported with its communication_id, idempotency_key, approval_id, draft_id, action_id and recipient, because clearing it is a human decision (check the sent mail) and not an automatable one.
  - OUTBOUND_FAILED must never be used for an outcome that cannot be proven never to have reached Gmail - that is what OUTBOUND_UNCERTAIN is for.
```

**Assertions.**

- Zero Communications rows have direction OUTBOUND_PENDING.
- Zero Communications rows have direction OUTBOUND_UNCERTAIN.
- Any such row that does exist must be reported with its communication_id, idempotency_key, approval_id, draft_id, action_id and recipient, because clearing it is a human decision (check the sent mail) and not an automatable one.
- OUTBOUND_FAILED must never be used for an outcome that cannot be proven never to have reached Gmail - that is what OUTBOUND_UNCERTAIN is for.

## `wf4-one-pending-approval-per-action`

- **Workflow**: wf4  |  **Unit under protection**: Approvals register - live approval uniqueness
- **Source QA workflow**: QA - Daily Report State Census (`3TVCLIVFGlBNSwK4`)

**Property.** No action has more than one PENDING approval at the same time.

**Why it exists.** Each end-to-end QA rerun of a drafting action raised a fresh approval request against a newer draft, leaving the older requests PENDING alongside the current one. The result was an action with several live approvals, any of which the owner could have decided - and deciding a stale one would send an out-of-date draft. QA - Approval Supersede Audit was written to clear exactly this state on one action.

**Query that would check it.**

```
GET https://sheets.googleapis.com/v4/spreadsheets/{SPREADSHEET_ID}/values:batchGet
    ?ranges=Approvals!A1%3AZ2000
    &valueRenderOption=UNFORMATTED_VALUE

then, over the returned rows:
  - Grouping Approvals rows by action_id, no group contains more than one row whose upper-cased status is PENDING.
  - An approval that has been overtaken by a later draft is marked SUPERSEDED with decision SUPERSEDED, not VOID, REJECTED or blank.
  - Superseding must be read-before-mutate: refuse if the target is absent, appears more than once, is already SUPERSEDED, is any status other than PENDING, or belongs to a different matter than the authorised one.
  - Superseding must be refused entirely unless the approval that is meant to survive is present exactly once and PENDING - leaving an action with no live approval is worse than leaving stale ones.
  - Each supersede writes exactly one audit Events row with event_id 'EVT-APPROVAL-SUPERSEDED-' + approval_id, so re-running updates that row rather than appending another.
```

**Assertions.**

- Superseding must be read-before-mutate: refuse if the target is absent, appears more than once, is already SUPERSEDED, is any status other than PENDING, or belongs to a different matter than the authorised one.
- Superseding must be refused entirely unless the approval that is meant to survive is present exactly once and PENDING - leaving an action with no live approval is worse than leaving stale ones.
- Each supersede writes exactly one audit Events row with event_id 'EVT-APPROVAL-SUPERSEDED-' + approval_id, so re-running updates that row rather than appending another.

- **Source QA workflow**: QA - Communications Delivery Key Census (`vrP4KZLwrsAbekc1`)

**Why it exists.** This is the exact cross-check the census was built to run. A PENDING approval whose earlier attempt was written under the old key format will, on decision, derive a 16-character key that matches nothing - so the gate's duplicate, pending and uncertain checks all look at an empty result set and the send proceeds as if it had never been attempted. The one-time append effect is harmless on decided approvals and dangerous on undecided ones.

  - The set of approval_ids appearing on old-8-char-key Communications rows and the set of PENDING approval_ids do not intersect.
  - Every Actions row with status AWAITING_APPROVAL is reported alongside its action_id, matter_id, draft_id and approval_id so an orphaned approval can be traced.
  - If the intersection is non-empty, the correct remedy is a human decision about the affected approval, not a key rewrite - rewriting a stored key would break the collision detection in check 7d, which relies on the key's own pre-image.
```

**Assertions.**

## `wf4-pending-approval-references-latest-draft`

- **Source QA workflow**: QA - Daily Report State Census (`3TVCLIVFGlBNSwK4`)

**Property.** Every PENDING approval references the highest draft version that exists for its action.

**Why it exists.** The gate refuses at decision time when a newer draft exists (STALE, 'Approve that one instead'), but a register full of PENDING approvals pointing at superseded drafts means the owner is repeatedly offered decisions that cannot be actioned. The census pairs each pending approval's draft_version with latest_version_for_action to make the gap visible before the owner hits it.

**Query that would check it.**

```
GET https://sheets.googleapis.com/v4/spreadsheets/{SPREADSHEET_ID}/values:batchGet
    ?ranges=Approvals!A1%3AZ2000
    ?ranges=Drafts!A1%3AZ3000
    &valueRenderOption=UNFORMATTED_VALUE

then, over the returned rows:
  - For each PENDING approval, the version of the draft it names equals the maximum version recorded for that approval's action_id.
  - Every PENDING approval's draft_id matches an existing Drafts row.

  - The gate's own STALE checks (content_hash equality against token_hash_or_reference, and latest-version-in-chain) must still fire independently at decision time; this invariant is about register hygiene, not a replacement for them.

## `wf5-actions-no-conflicting-status-on-one-action-id`

- **Workflow**: wf5  |  **Unit under protection**: Actions register integrity
- **Source QA workflow**: QA - Daily Report State Census (`3TVCLIVFGlBNSwK4`)

**Property.** Where an action_id does appear more than once, its rows must not disagree about status.

**Why it exists.** A duplicate row is recoverable if both copies say the same thing. Two rows for one action_id carrying different statuses means the register itself cannot answer whether the action is done, and 'last row wins' is a guess, not a fact. The census separates plain duplicates from conflicting duplicates for exactly this reason.

**Query that would check it.**

```
GET https://sheets.googleapis.com/v4/spreadsheets/{SPREADSHEET_ID}/values:batchGet
    ?ranges=Actions!A1%3AZ3000
    &valueRenderOption=UNFORMATTED_VALUE

then, over the returned rows:
  - For every action_id with more than one row, the set of upper-cased status values across those rows has size 1.
  - Any conflicting action_id is reported with every row's sheet row number, status and blocked_reason (first 60 characters).
  - The harness must not silently pick a winner between conflicting statuses.
```

**Assertions.**

- For every action_id with more than one row, the set of upper-cased status values across those rows has size 1.
- Any conflicting action_id is reported with every row's sheet row number, status and blocked_reason (first 60 characters).
- The harness must not silently pick a winner between conflicting statuses.
